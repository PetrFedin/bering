# Bering V34 — документальная сверка банковских распределений и контейнерной выручки

**Срез: 13 ноября 2026 года.** База разработки — V33, SHA `6281b6cf42fb90b3ae776887bfd2cbd1d82b0c63`, [Draft PR #33](https://github.com/PetrFedin/bering/pull/33). Версия **не меняет** `main`, реальные грузовые показатели, финансовые решения или состояние `HOLD`.

## Зачем нужен V34

В V33 по каждой строке отправки проверялись заявленные `invoice_total_minor`, `credit_note_minor`, `bank_paid_minor`. Но **один счёт** может относиться к нескольким контейнерам, а **одна банковская транзакция** может закрывать несколько счетов. Нельзя суммировать повторяющиеся значения из отгрузочных строк: это создаёт фиктивную выручку. Поэтому V34 добавляет контроль **уникальных банковских транзакций, счетов и распределений**, а не новые рыночные маршруты и не прогнозные TEU.

## Зерно и референциальная целостность

| Таблица | Ключ | Поля | Контроль |
|---|---|---|---|
| `invoices` | `invoice_token` | Заявленные SHA счёта и кредит-ноты, валюта, gross/credit (minor units), локатор | Уникальность токена и `(hash, locator)`, gross > 0, 0 ≤ credit ≤ gross, SHA кредит-ноты при credit > 0 |
| `bank_transactions` | `bank_transaction_token` | Hash выписки, дата, сумма в minor units, валюта, локатор | Уникальность токена и `(hash, locator)`, положительная сумма, дата не позднее 13.11.2026 |
| `allocations` | (`invoice_token`, `bank_transaction_token`) | Распределение положительной суммы | Оба внешних ключа существуют, совпадение валют, без повторов пар |
| `shipment_invoice_links` | (`scope`, `shipment_token`, `container_token`, `invoice_token`) | Распределение чистой суммы счёта по контейнерам | Один-к-одному с заявленными V33 shipment+invoice, включая группы |

**Инварианты:**

1. Для каждого счёта `net_i = gross_minor_i - credit_minor_i`.
2. `sum(allocations by invoice) ≤ net_i` — иначе счёт нельзя признать даже арифметически согласованным.
3. `sum(allocations by bank_transaction) ≤ bank_amount` — иначе одна банковская операция использована сверх её суммы.
4. `sum(shipment invoice apportionment by invoice) = net_i` — сумма счёта распределена по связанным контейнерам один раз, без повторного начисления.
5. Каждая строка V33 грузовой операции связана с V34 ровно один раз; повторяющийся **номер контейнера** при разных физических отправках сам по себе не доказывает двойной учёт.
6. Положительный результат — **только структурная согласованность представленных данных**. Даже при 100% совпадении заявленных сумм подлинность банк-операции, наличие груза, право на использование данных, подписанные счета и дополнительность остаются неподтверждёнными.

Уникальные идентификаторы — только маскированные токены, не имена контрагентов и не номера счетов/контейнеров. Выводы утилиты не печатают исходные токены и финансовые суммы: только агрегаты/коды ошибок.

## Проверенные сценарии

- Банк один, счета два: одно банковское поступление можно распределить по двум счетам, но не более общего платежа.
- Счёт один, контейнера два: сумма счёта распределяется на две отправки ровно один раз.
- Счёт общий для пилота и существующей группы: определяется как **потенциальный перенос**, а не как доказанный дополнительный груз.
- Частичный платёж: остаётся кандидатом на неоплаченную задолженность, не считается полностью закрытым.
- Дубли токенов или физической строки счёта/банковской выписки `(SHA-256 документа, локатор строки)` даже под разными токенами, отсутствующая SHA кредит-ноты, повторные пары распределения, потерянные внешние ключи, несовпадение валют, несовпадение хеша V33, будущая дата оплаты и небезопасные локальные пути — `INVALID`.
- Полностью **пустой** ввод — `NO_SOURCE_RECORDS_IN_SCOPE`, а не нулевая выручка или нулевой грузопоток.

## Запуск на правомерно полученных исходниках

В репозитории находится только [пустой шаблон](../data/evidence/V34_EMPTY_BANK_ALLOCATION_CONTRACT.json). Его **нельзя** заполнять фиктивными строками в Git. После согласования NDA и правомерного получения оригиналов хранятся два локальных файла **только** в исключённой из git папке `local_private/`:

- `local_private/v34_v33_source.json` — приватный V33 массив отправок, без персональных данных.
- `local_private/v34_bank_ledger.json` — V34 счета, банковские строки и распределения.

Поле `v33_source_sha256` в V34 должно равняться SHA-256 исходных **байтов** V33 файла; оба SHA передаются параметрами запуска. Это защищает от случайной подмены файла **между этапами**, но не подтверждает подлинность содержимого. Никакие оригинальные банковские выписки не загружаются в GitHub.

```bash
python3 scripts/v34_bank_allocation_gate.py
python3 -m unittest discover -s tests -p 'test_v34_*.py' -v
# Только при наличии легально полученных реальных локальных исходников:
python3 scripts/v34_bank_allocation_gate.py --repo . \
  --private-v33 local_private/v34_v33_source.json \
  --expected-v33-sha256 '<SHA-256 of actual source bytes>' \
  --private-ledger local_private/v34_bank_ledger.json \
  --expected-ledger-sha256 '<SHA-256 of actual ledger bytes>'
```

## QA фактически выполнено

В изолированном контейнере Python 3 доступны точные проверенные исходники модулей V32, V33 и нового V34. Выборочный итог в одном запуске: **113 / 113 PASS**; отдельно V32 — 31, V33 — 42, V34 — 40 тестов. Дополнительный однопроходный тест неправильных типов полей V34 не выявил аварийных исключений или ложного допуска (этот тест **не** является формальным property-based доказательством). Исходный полный приватный репозиторий в контейнере отсутствует, поэтому **невозможно заявить полный repository regression**. GitHub Actions GREEN на SHA V34 требуется проверить отдельно после публикации.

## Блокеры инвестиционного решения

- 12 категорий документов V32 — это **реестр запросов, не полученные 12 оригиналов**.
- 24 × (P1, P2, P3, GROUP_EXISTING) = **96 проверяемых monthly group slots**; в доступных базовых данных все **MISSING_NOT_ZERO**, подтверждено **0/96**, что не равно нулевому трафику.
- Реальные оплаченные новые 40ft: `null`; реальная дополнительная маржа группы: `null`; Bering NPV: `null`.
- Документы о согласовании 30k/150k TEU и итог экологической экспертизы МЛЦ, подписанные заверенные 24 месяца OD, банк/накладные/акты, независимые инженерная и финансовая приёмки — **не подтверждены**.
- GitHub-hosted jobs V33 завершались до предоставления списка шагов. Тексты Check Run annotations и account billing/runner entitlement **не установлены**, потому нельзя называть конкретную причину падения.

**Решение:** DRAFT / STRUCTURAL VALIDATOR IMPROVED / SOURCE EVIDENCE MISSING / CI NOT GREEN / P1–P3 HOLD / INVESTMENT HOLD. Задача V35 — обеспечить **фактический** сбор первых подписанных документов от надлежащих сторон и независимую сверку, а не автоматически производить доход из структурно валидного JSON.
