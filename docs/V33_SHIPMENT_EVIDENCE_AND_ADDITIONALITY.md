# Bering V33 — грузовой доказательный контур и защита от двойного учёта

**Контрольный срез: 13 ноября 2026 года.** Предыдущая версия: [V32](https://github.com/PetrFedin/bering/pull/32). Данный документ определяет воспроизводимую проверку качества данных, но **не удостоверяет перевозку, оплату, дополнительность или инвестиционную доходность**.

## 1. Главный пробел, обнаруженный в V32

V32 фиксирует 12 категорий необходимых доказательств и состояние `NOT_RECEIVED_NOT_ZERO`. Правильно, что это неизменяемый снимок, но он не умеет проверить будущую реальную таблицу перевозок на уровне физических отправок, связки счёт/банк, дублирования и перемещения существующего грузопотока между объектами группы. V33 добавляет **отдельный входной валидатор**, не меняя V32 и не снимая HOLD.

## 2. Проверяемая единица наблюдения

- **Покрытие:** 24 календарных месяца, октябрь 2024 — сентябрь 2026 включительно, для `P1`, `P2`, `P3`, `GROUP_EXISTING`: всего **24 × 4 = 96** комбинаций группа–месяц. Это не 96 грузов.
- **Отгрузочная запись:** один замаскированный идентификатор отправки и один замаскированный идентификатор физического контейнера. Различаются отдельные плечи и уникальные конечные отправки.
- **Объём:** 20-футовый контейнер = 1 TEU; 40-футовый = 2 TEU. Это *проверка единиц* для стандартных записей, не признание фактических количеств.
- **Оплата:** суммы передаются целыми строковыми значениями в минимальных денежных единицах соответствующей валюты: счёт, кредит-нота и оплаченная сумма. Равенство `paid = invoice - credit` свидетельствует **только о структурном совпадении заявленных цифр**; SHA приложений не проверяет подлинность выписки или банковскую проводку.
- **Дополнительность:** совпадение ключа `shipment_token + container_token` между пилотом и `GROUP_EXISTING` — возможный **внутригрупповой перенос**, не новая выручка. Одинаковый номер контейнера при разных отправках может отражать его повторное использование и **не доказывает каннибализацию**.

## 3. Два слоя контроля, которые нельзя объединять

| Слой | Что делает | Чего не устанавливает |
| --- | --- | --- |
| V33 структура | Типы, поля, период, пропуски, 20/40ft, TEU, дубли, последовательность дат, месячные итоги, формальная платёжная арифметика, пересечения ключей | Подлинность документов, реальное зачисление банком, статус подписей, доказанная дополнительность |
| Правовая и независимая проверка | Уполномоченный грузовладелец/перевозчик/банк/финансовый рецензент сверяют оригиналы и права доступа | Не заменяется unit-тестами и автоматическим выводом V33 |

Все 12 незакрытых категорий V32 остаются в своём архивном состоянии. Для каждого нового набора — новый датированный манифест, оригинал в контролируемом **не-Git** хранилище, hash, подпись владельца, аудиторская привязка к конкретной строке и отзыв независимого проверяющего.

## 4. Как использовать на авторизованном компьютере

Все исходные реальные данные должны быть правомерно получены. `local_private/` исключён из Git. Не размещать банковские выписки, реальные ISO номера контейнеров, названия клиентов и грузовые документы в репозитории.

```bash
python3 scripts/v33_shipment_proof_quality.py --repo .
python3 scripts/v33_shipment_proof_quality.py --repo . \
  --private-input local_private/v33_od_extract.json \
  --expected-sha256 <sha256_реально_полученного_файла> \
  --out local_private/v33_structural_receipt.json
python3 -m unittest discover -s tests -p 'test_v33_*.py' -v
```

При запуске **без исходных файлов** статус `NO_SOURCE_RECORDS_IN_SCOPE`, 96 слотов остаются неподтверждёнными и вся экономическая часть = `null`. При структурно корректном *частном* файле — `STRUCTURAL_REVIEW_REQUIRED`, **не `APPROVED`**. Некорректные данные → `INVALID` и код возврата 2. Скрипт не пересылает данные; поле `source_digest_is_authentication=false` по определению.

### Обязательное различение missing / zero

`monthly_coverage` может содержать `ATTESTED_ZERO` с числом 0 только как **утверждение файла, ещё требующее подтверждения исходным подписанным источником**. Пустые строки и не предоставленные месяцы нельзя преобразовать в 0. Даже полный набор `96/96` строк не меняет `confirmed_attested_months=0` без независимой проверки.

## 5. Пошаговый переход к инвестиционно пригодной модели

1. Получить законно допустимую 24-месячную OD-выгрузку с собственником данных и актом выгрузки, перечислить все 96 group-month slots, а не требовать 96 накладных.
2. Сопоставить `shipment_token` с оригинальными booking, B/L, gate event, receiving, счетом и кредит-нотой, затем — выпиской банка и датой поступления; проверить связь с валютой и налоговой базой.
3. Провести дедупликацию физических отправок и выявить внутригрупповую каннибализацию. Совпадение только container number — сигнал на ручную сверку, не основание двойного исключения.
4. Вычислить по **доказанным** партиям групповой дополнительный contribution margin: дополнительный net cash revenue минус действительно дополнительные переменные расходы минус утраченная маржа существующих активов; внешние независимые ревизоры подтверждают методику и единицы.
5. Только после CAPEX, графика ввода, OPEX, финансирования, налогов и WACC переходить к NPV / IRR. До этого числовые значения недопустимы.
6. Получить реальный GitHub Actions GREEN на конкретном SHA. На V32 попытки [#43456308353](https://github.com/PetrFedin/bering/actions/runs/43456308353) и [#43456308094](https://github.com/PetrFedin/bering/actions/runs/43456308094) закончились failure до доступных шагов. Их причина до сих пор не установлена; релиз остаётся HOLD.
