## Зачем V25, если V23/V24 уже существуют

V23 сверяет суммарную арифметику и уникальность экономических идентификаторов, V24 создаёт только условный прогноз **из доказанной месячной истории оплаченных новых контейнеров**. Ни одна модель не может быть достоверной, если один и тот же физический груз объявлен двумя новыми заказами: P3 (Китай → Владивосток → Магадан) уже содержит плечо Владивосток → Магадан, которое нельзя повторно продать как P1. Перемещение между существующими терминалами одной группы нельзя считать новой выручкой без вычета потери прежней групповой маржи.

Модуль scripts/source_join_v25.py требует:
- реестр **один контейнер 40ft = одна физическая запись** с псевдонимным стабильным SHA-подобным идентификатором и экономическим ID (из подлинных независимых документов);
- маршрутные события CHINA_VVO и VVO_MAG строго по пилоту; P3 должен содержать оба события, P1/P2 — VVO_MAG. Само событие перегрузки не образует новый спрос;
- проверенную исходную накладную, коммерческий договор, счёт, платеж, маржу, документ NEW / DIVERTED, 24-месячный baseline по группе и всех существующих терминалах; ссылки, даты, отправитель и независимый рецензент;
- для DIVERTED — старую групповую услугу и её маржу, документированную независимо;
- точную групповую единицу RUB **без НДС**; нет автоматического приведения FX/VAT;
- уникальные идентификаторы источников и событий затрат, запрет скрытого повторного отнесения фиксированных расходов или риска;
- **пооперационное** сопоставление идентичных физических отправок, новых/старых CM, классов и стоимости между V25 и V23; совпадение общих сумм без идентичности отправок недостаточно.

Формула screening:
для NEW: сумма(new group CM);
для DIVERTED: сумма(new group CM − incumbent group CM);
затем по каждому пилоту: − incremental fixed cost − incremental risk cost. Все показатели — screening incremental group contribution margin, не выручка, EBITDA, FCFF, NPV, налоговая прибыль и не признание денег на банковском счёте.

Отчёт может быть REVIEW_ONLY **только** при механически полных связанных источниках и положительной дельта-марже каждого пилота. При любой структурной ошибке INVALID; при недостающем документе HOLD, суммы не подменяются нулями. Во всех случаях bankable_revenue_approved=false и investment_approved=false. Два разных псевдонима всё ещё могут описывать один настоящий контейнер: без независимого перевода по исходным B/L, контейнерным номерам, контрагентам и событиям регистрация фиктивных ключей не исключается.

## Что в действительности протестировано

- 28 локальных unit-тестов Python 3.13.5 PASS на **полностью вымышленных** консигнациях, документах и суммах.
- Все 28 тестов сравнивают преднамеренно создаваемые ошибки. В синтетическом случае P1: 100−10−5=85 RUB; P2: (200−120)−10−5=65 RUB; P3: 50−5−5=40 RUB; группа 190 RUB. **Это тестовый арифметический контрпример, не реальная перевозка/прогноз/тариф/маржа.**
- Ошибки: повторная физическая отправка, два экономических ID для того же груза, дважды отражённое плечо P3, неполное плечо, дубликат события, повторный документ оплаты, отсутствие старой маржи, подменённый SHA, не независимый рецензент, не 24-месячная история, несовместимые VAT, группы и даты, несовпадение сумм V23/V25. Реальная банковская и накладная сверка не проводилась.
- Канонический data/pilots/V25_no_verified_consignments.json содержит 0 **предоставленных первичных записей**, а не «фактически нулевые отправки». Контроль возвращает HOLD и group_incremental_cm_rub=null.
- Приложен .github/workflows/v25-source-join-qa.yml; удалённый Actions GREEN не сертифицирован — предыдущие runner failures до запуска шагов, логи BlobNotFound, причина неизвестна. Нельзя менять арифметику ради обхода CI.
- Исходники V20 в бинарном виде в GitHub по-прежнему не доказаны в канонической цепочке; отдельный неполный источник в рабочей папке не заменяет одобренную загрузку/проверку.

## Правильно запросить источник для коммерческого допуска

Сначала получить **15 ранее подготовленных RFQ** с согласованным отправителем и правовым основанием, два сопоставимых D2D предложения с датой и НДС, затем доступ к обезличенному реестру реально исполненных 24 месяцев OD по всем терминалам одной экономической группы. Для каждого из P1/P2/P3 нужны независимые отправитель, получатель, 40ft тип, пломба/контейнер и B/L, маршрутные даты, вес, цена ex VAT, отдельные портовые и last mile расходы, банковское подтверждение платежа, перенос и каннибализация существующей маржи. Документы обрабатываются при наличии прав и с раздельными проверяющими. Без NDA/разрешений не хранить оригинальные коммерческие документы в публичных PR.

Следующий релиз допусков: 1) независимое подтверждение source IDs; 2) V23↔V25 source-level exact join; 3) восстановление CI; 4) связь исходного помесячного реестра V25 с агрегатами V24 и out-of-time прогнозом; 5) независимая калькуляция D2D; 6) сценарный FCFF/NPV/потребность в оборотном капитале с CAPEX, сезонностью, простоями и правовыми ограничениями.

**Решение:** P1=P2=P3=HOLD. Нет доказанной дополнительной платёжеспособной загрузки или маржи. Работа с новым ТЛК не смешивается с межконтинентальным тоннелем и будущей железной дорогой. Никаких прав на инвестиционные выводы и PR merge до восстановления реальных источников и CI.
